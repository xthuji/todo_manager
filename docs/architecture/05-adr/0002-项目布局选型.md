# ADR-0002：项目布局选型（扁平 app/ 而非 internal/pkg）

- 状态：已接受
- 日期：2026-08-01
- 决策者：项目维护者

## 背景

Go 社区有 [golang-standards/project-layout](https://github.com/golang-standards/project-layout) 约定，建议 `internal/`（私有包）+ `pkg/`（可复用库）+ `cmd/`（入口）的分层。Todolist-Go 需决定是否遵循。

## 决策

采用**扁平的 `app/` 顶层布局**：

```
todolist-go/
├── app/
│   ├── cmd/          # 入口（仍遵循 cmd 约定）
│   ├── routes/
│   ├── services/
│   └── utils/
├── data/
├── static/
└── tests/
```

未使用 `internal/` 与 `pkg/` 分层。

## 理由

1. **单应用项目，无对外可复用库**：所有代码只为 Todolist-Go 服务，不会作为库被其他 Go 项目 import，无需 `pkg/` 暴露。
2. **无外部消费者，无需 internal 强约束**：`internal/` 的作用是阻止外部项目 import，但本项目本身不对外发布 Go 库，强制 `internal/` 反而增加路径长度。
3. **与 Python 版结构对齐**：Python 版用 `app/routes/` `app/services/` `app/utils/`，Go 版保持一致便于对照迁移。
4. **路径简短**：`app/services/weather` 比 `internal/services/weather` 更短，import 语句更清爽。

## 备选方案

| 方案 | 放弃原因 |
|---|---|
| 严格 `internal/` + `pkg/` | 路径变长，无实际收益（无对外库） |
| 单 `main` 包扁平 | 文件过多，无包级隔离 |
| 领域驱动 `domain/application/infrastructure` 分层 | 项目规模小，DDD 过度设计 |

## 后果

**正面**：

- import 路径短：`todolist-go/app/services`
- 目录结构直观，新人易理解
- 与 Python 版一一对应

**负面**：

- 不符合社区主流约定，习惯 project-layout 的开发者需适应
- 若未来要抽取某个包为独立库，需迁移路径（影响 import）
- `tests/` 作为独立 package（`package tests`），与源码包分离，跨包测试不便
