# ADR-0006：错误处理策略选型

- 状态：已接受
- 日期：2026-08-01
- 决策者：项目维护者

## 背景

Go 推荐的错误处理方式是 `error` 接口 + `errors.Is/As` + `fmt.Errorf("%w", err)` 包裹。项目需决定采用何种风格。

实际代码中大量出现：

- 函数返回 `map[string]interface{}` 而非 `(T, error)`
- 用 `"error"` key 携带错误信息
- 类型断言静默忽略 `m, _ := x.(T)`
- `fmt.Errorf("...: %v", err)` 而非 `%w`

## 决策

**采用轻量错误处理**，不引入自定义 error 类型与错误码体系：

1. 业务函数返回 `map[string]interface{}`，失败时塞入 `"error"` key（如 [FetchCMAWeather](file:///Users/huji/work/MyProject/code_mine/gitee/todo_manager/todolist-go/app/services/weather/weather_cma_service.go#L61)）
2. HTTP handler 直接构造状态码与响应 JSON，无统一错误中间件
3. 多源错误收集为字符串切片（[checkWeatherError](file:///Users/huji/work/MyProject/code_mine/gitee/todo_manager/todolist-go/app/services/weather_service.go#L436)）
4. 类型断言用 `_, ok :=` 或 `_ :=` 模式，失败返回零值

## 理由

1. **与 Python 版对齐**：Python 版用 dict 携带 error，Go 版保持一致便于对照迁移。
2. **响应结构灵活**：前端对响应结构要求宽松，不同端点字段不同，map 比 struct 更灵活。
3. **单机应用无错误码需求**：无客户端需要按错误码做分支，错误信息直接展示给用户即可。
4. **代码量少**：无需定义 error 类型、错误码常量、错误转换函数。

## 备选方案

| 方案 | 放弃原因 |
|---|---|
| 自定义 error 类型 + `errors.Is/As` | 需定义类型层次，代码量增加；前端不消费 error 类型 |
| 错误码体系（如 10001=参数错误） | 单机应用无意义，错误信息直接展示即可 |
| `(T, error)` 标准返回 | 与 Python 版差异大，迁移成本高；多源聚合时类型不一致 |
| `fmt.Errorf("%w")` 包裹链 | 上层无 `errors.Is/As` 使用场景，包裹无收益 |

## 后果

**正面**：

- 代码与 Python 版一一对应，迁移与对照容易
- 响应结构灵活，前端契约宽松
- 无类型定义开销

**负面**：

- **类型安全弱**：编译期无法检查字段拼写错误，运行时才发现
- **错误传播链断裂**：`%v` 而非 `%w`，上层无法 `errors.Is`，调试时丢失原始错误
- **静默失败多**：`m, _ := x.(T)` 模式隐藏类型不匹配问题
- **重构困难**：字段名变更无编译期保护，需全局搜索替换
- **新人理解成本**：缺乏明确的错误契约，新人需读代码才能判断失败模式

## 复审建议

未来若项目复杂度上升，可考虑：

1. 为核心数据结构定义 struct（如 `WeatherData`/`LocationResult`），保留 map 仅用于序列化边界
2. 外部 API 调用层用 `(T, error)`，业务层维持 map
3. 至少在 `fmt.Errorf` 中用 `%w` 包裹，保留错误链
