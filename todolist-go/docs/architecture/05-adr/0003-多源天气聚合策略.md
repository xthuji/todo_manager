# ADR-0003：多源天气聚合策略

- 状态：已接受
- 日期：2026-08-01
- 决策者：项目维护者

## 背景

天气数据对个人用户至关重要（决定是否带伞、穿衣等），但单一数据源存在以下问题：

- **更新延迟**：天气网可能比 CMA 慢 30 分钟
- **字段缺失**：墨迹无逐小时预报，天气网无生活助手
- **服务故障**：单源宕机时无法降级
- **历史数据不全**：天气网的日历天气对历史日期字段稀疏，墨迹更完整

需要决定如何整合多源数据。

## 决策

采用**并行抓取 + 字段级合并 + 完整性门控缓存**策略：

1. **4 个数据源 7 路并行抓取**（[QueryWeatherData](file:///Users/huji/work/MyProject/code_mine/gitee/todo_manager/todolist-go/app/services/weather_service.go#L326)）：
   - 墨迹（liveWeather + calendarWeather）
   - 天气网（liveWeather + hourlyWeather + lifeHelper + recentDays + calendar）
   - CMA（liveWeather）
   - NMC（liveWeather + dailyWeather）
2. **今日天气按更新时间取最新**：[BuildWeatherData](file:///Users/huji/work/MyProject/code_mine/gitee/todo_manager/todolist-go/app/services/weather_service.go#L117-L119) 按 `time` 字段降序排序，主数据取最新源，再合并其他源的非空字段。
3. **特定字段固定来源**：hourlyWeather/lifeHelper 仅取天气网；recentDays 优先天气网回退 NMC。
4. **日历天气历史补齐**：用墨迹的 calendarWeather 补齐今日之前的字段。
5. **完整性门控**：仅当 8 项数据全部非空才写入缓存（[weather_service.go#L315](file:///Users/huji/work/MyProject/code_mine/gitee/todo_manager/todolist-go/app/services/weather_service.go#L315)）。
6. **过期缓存兜底**：`AllowExpired=true`，缓存未命中或过期时仍可返回旧数据。

## 理由

1. **并行抓取**：7 路 API 总耗时 ≈ 最慢的一路（约 10s），而非 7 倍累加。
2. **时间优先合并**：天气数据有时效性，更新更晚的数据更可信。
3. **字段固定来源**：避免不同源的字段定义差异导致数据错乱。
4. **完整性门控**：避免缓存"半成品"数据导致前端展示异常。
5. **过期兜底**：所有源都失败时仍能返回上次成功的数据，提升可用性。

## 备选方案

| 方案 | 放弃原因 |
|---|---|
| 单一数据源 | 可用性与完整性不足 |
| 顺序抓取（失败再下一个） | 总耗时高（最坏 7×10s=70s） |
| 投票合并（多源相同才采用） | 数据源字段定义不同，无法直接投票 |
| 完全合并（无时间优先） | 可能用过期数据覆盖新数据 |
| 无门控缓存 | 缓存不完整数据，前端体验差 |

## 后果

**正面**：

- 数据完整性与时效性兼顾
- 单源故障可降级
- 缓存数据质量高

**负面**：

- 实现复杂度高（[BuildWeatherData](file:///Users/huji/work/MyProject/code_mine/gitee/todo_manager/todolist-go/app/services/weather_service.go#L78-L323) 约 250 行）
- 完整性门控过严：任一源故障则不缓存，下次请求仍需全量抓取
- 字段固定来源硬编码，扩展新源需改代码
- 7 个 goroutine 同时请求外部 API，无并发限流，可能被反爬
