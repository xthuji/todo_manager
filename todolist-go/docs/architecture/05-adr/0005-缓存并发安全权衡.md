# ADR-0005：缓存并发安全权衡

- 状态：已接受（待复审）
- 日期：2026-08-01
- 决策者：项目维护者

## 背景

[CacheUtil](file:///Users/huji/work/MyProject/code_mine/gitee/todo_manager/todolist-go/app/utils/cache_util.go#L38) 是项目的核心基础设施，被路由层与服务层广泛使用。其内部 `memoryCache map[string]*MemoryCacheItem` **未加锁**。

对比：[ConfigUtil](file:///Users/huji/work/MyProject/code_mine/gitee/todo_manager/todolist-go/app/utils/config_util.go#L23) 的 `configCache` 已用 `sync.RWMutex` 保护。

## 决策

**暂不为 `memoryCache` 加锁**，接受单机桌面应用场景下的低并发风险。

## 理由

1. **单用户桌面应用**：理论上并发度极低，同一时刻最多 1-2 个 HTTP 请求。
2. **大多数写操作串行**：缓存写入发生在主 goroutine 收集完所有结果后（如天气查询的 fan-out 之后），并发 goroutine 仅读不写。
3. **map 操作的"实际安全"**：Go 的 map 并发读写不一定立即崩溃，常需 `go test -race` 才能检测；当前测试未覆盖高并发场景，问题未暴露。
4. **加锁开销**：每次 `GetWrappedData` 都要锁会引入轻微延迟，对桌面应用的响应敏感场景不友好。
5. **文件缓存的兜底**：即使内存 map 出问题，文件缓存仍可正确返回数据。

## 备选方案

| 方案 | 评估 |
|---|---|
| `sync.RWMutex` 全保护 | 最直接，但读写都需锁，热点路径有开销 |
| `sync.Map` | 专为读多写少优化，但 API 不如普通 map 自然；value 是 `*MemoryCacheItem` 指针，存取需额外处理 |
| 分片锁（sharded map） | 过度设计，单机桌面场景无收益 |
| 不可变 map + 原子替换 | 写时复制整个 map，GC 压力大 |

## 后果

**正面**：

- 代码简单，无锁开销
- 当前场景下功能正常

**负面**：

- **理论竞态**：多 goroutine 并发写同一 key 可能 panic（Go runtime 检测到 map 并发写会直接 fatal error）
- **未来扩展受限**：若引入后台定时任务并发刷新缓存，风险上升
- **不一致**：与 `ConfigUtil` 的加锁风格不统一，新人易混淆
- **测试盲区**：`go test -race` 可能报告竞态

## 复审建议

建议在下一次重大重构中：

1. 用 `sync.RWMutex` 包裹 `memoryCache` 的所有访问点（与 `ConfigUtil` 风格统一）
2. 添加 `go test -race` 到 CI
3. 在 [07-dev-guide.md](07-dev-guide.md) 的代码规范中明确"全局 map 必须加锁"
